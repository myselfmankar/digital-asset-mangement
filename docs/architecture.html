Database Schema

Entity Relationship Overview

PhotoStack AI uses a normalized PostgreSQL schema with strategic relationships for optimal performance and flexibility.

Entity Relationship Diagram

erDiagram images ||--o| metadata : "has one" metadata ||--o| locations : "has one" images }o--o{ tags : "tagged with" images }o--o{ albums : "belongs to" images { int id PK string filename UK "Unique constraint" string filepath datetime upload_date string resolution int image_size string mimetype string status "processing|completed|failed" boolean is_favorite string phash "Perceptual hash for duplicates" } metadata { int id PK int image_id FK string camera_model datetime date_taken "EXIF DateTimeOriginal" float f_number "Aperture" string exposure_time "Shutter speed" int iso string focal_length string lens_model json raw_exif "Full EXIF dump" } locations { int id PK int metadata_id FK float latitude float longitude string address "Reverse geocoded" } tags { int id PK string name UK "Unique constraint" } albums { int id PK string name string description }

Key Relationships

Type Entities Rationale
1:1 Image → Metadata Not all images have EXIF; separation keeps images table lean
1:1 Metadata → Location GPS is optional; location is extension of metadata
M:N Images ↔ Tags One image has multiple tags; one tag applies to many images
M:N Images ↔ Albums One image can be in multiple albums (e.g., "2023 Summer" + "Beach Photos")

Header: x-goog-api-key Gemini-->>Service: AI Response Note over Env,Gemini: Key never exposed to frontend

Security Best Practices

  • API keys stored in environment variables (never in code)
  • Photos processed locally (self-hosted)
  • CORS configured for specific origins
  • No third-party analytics or tracking
  • Pydantic validation on all API inputs
